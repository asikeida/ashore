# Git 与提交规范

本项目的 Git 模型已按单人本地开发裁剪：**不使用 Issue、Pull Request、CI/CD 和远程门禁**。纪律完全依赖本地约定，因此每一条都要当真。

## 1. 总体工作流

```text
规划条目 → 从最新 main 创建短期分支 → 小步提交 → 本地验证 → merge --no-ff 回 main → 删除分支
```

- `main` 必须始终可构建、可测试通过；合并回 `main` 前必须全量 `./mvnw test` 绿灯。
- 不要直接在 `main` 上开发正式功能。
- 仓库初始化是唯一例外：首个最小工程骨架与规则文档可以直接提交到 `main`，之后立即进入分支流程。
- 一个里程碑可以包含多个任务条目；一个任务条目可以包含多个清晰 commit。不要把"一个阶段"机械地压成一个巨大提交。

## 2. 分支命名

分支格式：

```text
<类型>/<简短主题>
```

规则：

- 类型使用小写英文；主题同时包含小写英文范围与中文目标，以连字符连接，例如 `infra/logging-日志基础`。
- 主题说明目标，不使用姓名、日期或无意义编号。
- **合并后保留分支指针作为留档**（2026-11-03 决策）：merge 后不删除分支，远程推送时一并 push，GitHub Branches 页面按 Merged 分组归档。同主题的后续迭代不复用旧分支名——追加序号或新主题命名（如 `feat/auth-login2-扫码登录`）。
- 从最新 `main` 创建；如果 `main` 有新提交，优先在合并前同步并解决冲突。

推荐类型：

| 类型 | 使用场景 | 示例 |
| --- | --- | --- |
| `feat` | 新用户能力 | `feat/auth-账密登录` |
| `fix` | 修复缺陷 | `fix/comment-回复丢失` |
| `infra` | 本地环境、容器、依赖、启动 | `infra/db-本地mysql基线` |
| `docs` | 文档和协作规则 | `docs/开发规划` |
| `refactor` | 不改变外部行为的代码整理 | `refactor/api-统一异常处理` |
| `test` | 补充或修正测试 | `test/rank-积分幂等` |
| `chore` | 依赖、构建或仓库杂项 | `chore/升级依赖` |

## 3. Commit 格式

提交遵循 Conventional Commits 的结构，说明使用中文：

```text
<类型>(<范围>): <中文摘要>
```

范围可选。它应使用与代码模块一致的小写英文，例如 `auth`、`article`、`comment`、`api`、`db`。

推荐示例：

```text
chore: 初始化 Ashore 工程骨架
docs: 建立协作规则与开发规划
infra(db): 添加本地 MySQL 与 Flyway 基线
feat(auth): 新增账号密码注册登录
feat(article): 支持面经发布与状态机流转
fix(comment): 修复子回复父级丢失
refactor(api): 提取统一异常处理
test(rank): 补充积分幂等测试
```

提交摘要要求：

- 使用动词开头，例如"新增""修复""添加""调整""提取""删除"。
- 说明实际结果，不写"更新""修改一下""优化代码"等模糊文字。
- 一行完成，避免句号和无意义英文缩写。
- 一个提交只完成一个可审核意图；不要把无关格式化、依赖升级和业务功能混在一起。

复杂提交可以在正文记录原因、验证结果和规划锚点：

```text
feat(article): 支持面经发布与状态机流转

为面经创建、REVIEW→ONLINE 状态流转和正文版本化建立最小闭环。

验证：./mvnw test
规划：docs/开发规划/03-M3面经域实施计划.md §2
```

## 4. 提交如何拆分

拆分依据是"能否独立理解和验证"，不是文件数量。

以下内容应放在同一个提交：

- 一个功能所必需的 Controller、Service、DTO、Mapper 和测试。
- 某次数据库迁移及依赖该迁移的代码。
- 某个基础设施配置及其本地启动说明。
- 一项接口变更及其 OpenAPI、测试和接口说明文档。

以下内容应拆成不同提交：

- 业务功能与无关依赖升级。
- 数据库基础设施与后续业务功能。
- 独立可验证的重构与行为变更。
- 临时调试修改与正式实现。

如果中间提交不能独立构建或测试，不要为了凑"提交数量"强行拆分。

## 5. 规划与任务追踪（替代 Issue）

- 里程碑与任务记录在 `docs/开发规划/` 的编号文档中，每个任务条目写明验收方式。
- 开工前先在规划文档中登记任务（相当于建 Issue），完成后勾选。
- 发现的技术债与暂缓事项记入 `docs/开发规划/90-待办清单.md`，代码内 TODO 必须带规划锚点（见 `05-注释与命名规范.md`）。

## 6. 合并、发布与时间记录

- 功能分支验证通过后 `git merge --no-ff`，合并提交信息格式：`merge: <分支主题>`，例如 `merge: infra/db-本地mysql基线`。保留分支脉络，让 main 历史呈现清晰的交付单元。
- 合并后保留分支作为留档（见 §2）；推送远端时除 main 外显式推送各分支。
- 每个可运行演示版本打标签，例如 `v0.1.0`。
- 发布说明记录新增能力、升级步骤、数据库迁移和已知限制。
- **Git 提交日期应反映真实开发或迁移发生时间；不要为了制造项目履历伪造历史。**

## 7. 权限

- 未经用户在当前任务明确要求，不执行任何 Git 写操作：`init`、`commit`、`merge`、`push`、`rebase` 或历史改写。
- 后端变更：合并前运行相关测试；必要时运行 `./mvnw test` 或 `./mvnw package`。
- 接口变更：验证成功、校验失败、未登录、无权限和关键业务失败场景。
- 部署或环境变更：验证配置样例、健康检查和数据持久化说明。
