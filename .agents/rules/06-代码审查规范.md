# 代码审查规范

代码审查的目标是确认改动正确、可维护、可验证，并让项目的整体健康度不因小改动持续下降。本项目不使用 Pull Request，审查发生在**合并回 main 之前的自查**与 `.local/代码审核/` 的书面记录中——把它们当作未来自己和面试官可以读懂的交付说明。

## 1. 合并自查前

作者应确保：

1. 分支只解决一个明确任务，不混入无关重构或全文件格式化。
2. 代码、测试、数据库迁移、配置和文档与改动范围一致。
3. 已执行与风险匹配的验证（至少相关测试；合并前全量 `./mvnw test`），并在审核记录写明命令和结果。
4. 新增依赖、中间件、环境变量和安全影响已说明。
5. 没有密钥、日志、构建产物、个人路径或测试数据泄漏。

当改动影响用户如何构建、测试或使用项目时，README、接口说明或规划文档必须同步更新。

## 2. 审查内容

审查时不只看 diff 的几行，要阅读相关方法、类和调用上下文。重点检查：

- 功能是否满足规划文档中登记的验收条件。
- 命名、模块边界和抽象是否清晰，是否引入不必要复杂度。
- 鉴权、资源归属过滤、输入校验、异常和日志是否完整。
- 数据库查询是否存在 N+1、缺失索引、无过滤分页或遗漏归属条件的风险。
- 事务范围是否正确，是否在事务中执行远程调用、文件操作或长耗时任务。
- 测试是否覆盖关键成功和失败场景，而不是只验证实现细节。
- 接口契约、OpenAPI 和用户文档是否与行为一致。

看不懂的代码应停下来澄清，而不是假定它正确。无法解释清楚的实现通常也难以维护。

## 3. 问题分级

自查与审核记录中使用中文写清问题与理由，并按影响区分：

| 标记 | 含义 | 是否阻塞合并 |
| --- | --- | --- |
| `阻塞：` | 正确性、安全、数据、兼容性或明显质量问题 | 是 |
| `建议：` | 能明显改善可维护性或测试性的改进 | 通常是 |
| `问题：` | 需要解释设计取舍或行为 | 解释后决定 |
| `Nit：` | 非强制的格式或措辞建议 | 否 |

个人偏好不能作为阻塞理由。已有明确规则时按规则执行；没有规则时优先保持现有代码风格，并将值得推广的共识补入规范。

## 4. 审查结论

- 所有阻塞项解决或有记录的替代方案后才能合并。
- 对未处理的建议，应在审核记录中说明接受、拒绝或转入待办清单的原因。
- 合并通过后，确认审核记录中的验证结果、文档和规划勾选没有过期。
- 合并后删除功能分支；若发现回归，以新分支和新提交修复，不在已合并提交上静默改写历史。
