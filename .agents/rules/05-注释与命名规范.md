# 注释与命名规范

## 1. 命名是第一层文档

优先通过准确的英文命名表达含义，避免让注释替代码翻译名称。

- 包名全小写，使用英文单词，不使用拼音、下划线或无意义缩写。
- 类、接口、枚举使用 UpperCamelCase，名称表达领域概念或职责，例如 `InterviewPostPublishService`。
- 方法、参数、局部变量使用 lowerCamelCase，名称表达动作或状态，例如 `publishInterviewPost`、`authorId`。
- 常量使用 UPPER_SNAKE_CASE，名称表达不可变业务含义，例如 `MAX_TITLE_LENGTH`。
- 布尔值使用能读成判断句的名称，例如 `isPublished`、`hasAccess`、`canRetry`。
- 缩写只使用广泛约定的技术术语，例如 `URL`、`HTTP`、`ID`、`DTO`。不要自创缩写。
- 名称不应携带无用实现细节，例如避免 `userServiceImpl2`、`dataProcessUtil`。

## 2. 何时写 Javadoc

`/** ... */` 是 Java 的 Javadoc，用于说明调用者需要知道的契约。它不应被禁止。

以下场景必须或应当使用 Javadoc：

- 对其他模块暴露的公共接口、扩展点和非直观的 public 方法。
- 配置属性类，说明配置项的用途、单位、默认行为和安全影响。
- 业务术语不明显的领域类型、值对象和枚举（例如文章状态机的各状态语义）。
- 有重要前置条件、返回约束、异常语义或副作用的方法。

Javadoc 应说明如何使用、输入输出约束、失败语义和必要的限制。简单 getter、显而易见的构造器、只在本类使用的私有辅助方法不要求为了形式补 Javadoc。

示例：

```java
/**
 * 发布面经并进入审核状态。
 *
 * @throws AccessDeniedException 当前用户处于封禁状态时抛出
 */
InterviewPostVo publish(PublishInterviewPostReq req);
```

## 3. 行内和块注释

- 单行 `//` 注释用于解释代码本身无法表达的"为什么"：业务取舍、兼容性原因、边界条件或外部系统限制。
- 复杂算法、状态机或不直观分支可以使用 `/* ... */` 块注释说明整体思路。
- 注释优先使用中文；协议名、类名、配置名、代码标识符保留英文。
- 不注释显而易见的代码，例如"获取用户""循环列表""返回结果"。
- 注释修改后必须与代码一致；过期注释比没有注释更危险。

好的注释：

```java
// 积分先写 Redis hash 做当日幂等，防止取消后重放重复加分。
activityRankService.recordIfAbsent(userId, action);
```

无价值注释：

```java
// 保存文章
articleMapper.insert(article);
```

## 4. TODO 和临时方案

不允许无归属、无期限的 `TODO`、`FIXME` 或"临时实现"留在正式代码中。

确实需要暂缓的工作，必须先登记到 `docs/开发规划/90-待办清单.md`，并写成可追踪格式：

```java
// TODO(待办#M5): 搜索服务接入 ES 后启用高亮返回。
```

对应任务完成前应删除 TODO。不能用返回 `null`、空集合、固定成功结果或模拟数据来伪装未完成实现；测试夹具和明确标识的开发样例除外。

## 5. Java 注解与 Lombok

- 重写父类或实现接口的方法，在语言允许时使用 `@Override`。
- API 请求对象用 Bean Validation 注解表达输入约束。
- 持久化实体优先使用 `@Getter`/`@Setter`；确需 `@Data` 时，必须确认生成的 `toString`、`equals`、`hashCode` 不包含敏感字段（密码、令牌）与超大字段（正文内容）。
- DTO 可优先使用 Java `record` 表达不可变数据；需要 Lombok 时按实际需求选择注解，不机械叠加。
- `toString` 不输出密码、令牌或完整正文内容。

## 6. 格式化

当前阶段遵循现有代码风格：四空格缩进、一个顶级 public 类对应一个文件、导入有序、避免为了对齐而改动无关行。

不要将大范围格式化与功能改动放在同一提交。
