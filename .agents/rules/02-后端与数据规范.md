# 后端与数据规范

## 1. Spring Boot 与业务层次

- Controller 只处理 HTTP 参数、身份入口、调用服务和返回响应，不承载复杂业务规则。
- Service 负责用例编排、权限判断、事务边界和跨模块协调。
- Mapper（`@Mapper` 接口）负责持久化查询，不在 Controller 中直接拼接数据库逻辑；复杂 SQL 用 XML 或注解写清，不做隐式魔法。
- MyBatis-Plus 的 `IService`/`ServiceImpl` 只用于真正通用的单表 CRUD 编排；不为每个实体机械生成一层空壳 Service。
- DTO 用于 API 边界；不要直接把数据库实体作为请求或响应对象暴露。
- 新增请求对象使用 Bean Validation 表达可验证约束，并为校验错误提供一致输出。

## 2. 数据归属与权限

- 所有用户数据都应有明确归属，例如作者、用户、文章或评论。
- 查询、更新和删除必须验证当前用户是否有权访问目标数据。
- 不因为前端隐藏了按钮就省略后端鉴权。
- 多表查询和列表查询必须检查是否遗漏归属过滤条件（未登录可见范围、作者本人、管理员）。

## 3. MyBatis-Plus 与事务

- 先写清楚表结构、索引和约束（Flyway DDL），再实现实体与 Mapper。
- 避免在循环中触发单条查询（N+1）；批量场景用 in 查询、关联查询或显式分批。
- 分页使用 `Page` 对象且必须显式携带查询条件与排序，禁止无过滤全表分页。
- 事务放在 Service 的用例边界；不为省事给只读操作加写事务，不在事务中执行远程调用或长耗时任务。
- 不依赖任何自动建表/改表机制。

## 4. Flyway 与数据库迁移

- 从第一张持久化业务表开始使用 Flyway 管理结构变更（`flyway-mysql`，脚本 `V{n}__中文描述.sql`）。
- 每次表结构、索引、约束或必要基础数据变化，都新增一个不可修改的版本化迁移脚本。
- 已在共享环境执行过的迁移脚本不能随意改写；需要修正时创建新的迁移。
- 迁移脚本和依赖它的代码放在同一功能提交中。

## 5. 异步与中间件

- Redis、Elasticsearch、消息队列只在对应业务需求出现后引入（会话与计数预计在 M2 引入，搜索在 M5）。
- 异步任务必须有状态、幂等策略、失败记录和可重试方式。
- 关系数据、短期缓存和检索索引要有明确职责，不能互相替代。
- 引入一个新基础设施时，补充本地启动方式、配置说明、健康检查和关键失败场景。
